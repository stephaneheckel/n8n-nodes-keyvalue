# Building an n8n Community Node: What We Learned Building KeyValue

We followed the official n8n tutorial for building a programmatic-style node as our starting point. The tutorial walks through creating a FriendGrid node that wraps the SendGrid API, covering scaffolding, the difference between programmatic and declarative styles, UI property definitions, the execute method, credential setup, and npm packaging. We adapted its structure for our own node: a filesystem-based key-value store called KeyValue.

From there, the process unfolded in stages. First, we scaffolded the project from the n8n-nodes-starter template, removed the example files, and created our node directory with the required three files: a TypeScript implementation, a JSON codex file for metadata, and an SVG icon. We installed dependencies and handled the ESLint peer conflict with the legacy peer deps flag. The TypeScript file defined two resources — Directory and Record — each with its own set of operations exposed through n8n's UI property system using displayOptions to show or hide fields based on the selected resource and operation.

Next, we implemented the execute method. Every operation routes through a loop that reads parameters by index, performs the filesystem action, and pushes result objects with pairedItem to preserve item linking. Errors are wrapped in NodeApiError with itemIndex for proper error attribution. The linting step caught common issues: missing pairedItem, unsorted operation options, missing subtitle, and raw error throws. We fixed each one iteratively until the build and community node lint rules both passed with zero errors.

We then adapted the output format for list operations. Instead of returning a single nested array, we produced one item per entity so users can pipe results directly into downstream nodes. We added optional glob filtering on directory and record names, and a substring filter on record content. An Append operation with a configurable separator rounded out the record operations.

Cross-platform compatibility came from using Node.js abstractions exclusively. The base directory uses os.homedir() and path.join() so the same code runs on Windows and Linux without modification. We added an environment variable to override the default path, documented its interaction with n8n's file access restriction setting, and included a step-by-step Docker persistent storage guide in the README.

Publishing to npm required cleaning the package tarball. We removed build artifacts and duplicate files from the dist directory, dropped the incorrect main field from package.json since n8n loads nodes through its own n8n.nodes array, and verified the tarball contents with npm pack. The first install on a Docker VPS hit the known n8n core loader bug where the node fails with "Class could not be found" despite correct exports. The fix was clearing node_modules and package-lock.json from the community nodes directory and reinstalling.

We tested on both Windows 11 and a Linux Docker VPS. Every operation worked correctly on both platforms. Persistent storage was confirmed by setting N8N_KEYVALUE_DIR inside the Docker volume mount. The entire project, including a full README with operation reference and setup guide, lives in a single TypeScript file, a JSON codex file, an SVG icon, and a standard npm package.json with no external dependencies beyond n8n-workflow and Node.js built-ins.
